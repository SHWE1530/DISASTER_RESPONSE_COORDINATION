# Stage 02 — Deep Learning (Disaster Response Coordination)

Two deployed models: a **CNN** that classifies whether a camera/drone scene is
flooded, and an **LSTM** that forecasts river water level from recent readings.

> Every number in this document is regenerated by
> `python Stage02_DL/03_dl_engineer.py` followed by
> `python Stage02_DL/04_evaluation_engineer.py`, and is read from
> `data/outputs/dl_training_metrics.json` and `data/outputs/evaluation_metrics.json`.

---

## 1. Mission

Stage 01 reasons over numeric thresholds. Stage 02 adds two things thresholds
cannot give you: **visual confirmation** that a road is actually under water,
and a **short-horizon forecast** of where the river is heading.

## 2. CNN — flooded / unflooded scene classification

### Data

| Split | Images | Flooded | Unflooded |
| --- | ---: | ---: | ---: |
| Train | 350 | 70 | 280 |
| Validation | 75 | 15 | 60 |
| Test | 75 | 15 | 60 |
| **Total** | **500** | **100** | **400** |

Stratified 70/15/15. The split is written to
`data/outputs/cnn_split_manifest.json` **by file path**, and the evaluation
script replays that manifest rather than re-deriving the split from a seed —
`ImageFolder` ordering is a filesystem property, so a seed alone does not
guarantee the same held-out set on another machine.

> **Sample-size caveat, stated up front.** The test set contains **15 flooded
> images**. A flooded recall of 0.9333 means 14 of 15 — one image moves it by
> 6.7 points. Because that is too thin to support a precise claim,
> `06_cross_validation.py` runs 5-fold stratified CV over all 500 images and is
> the source you should quote. See section 2b.

### Architecture and preprocessing

Three controlled experiments were benchmarked:

| Experiment | Architecture | Balancing |
| --- | --- | --- |
| `Baseline_3Layer_CNN` | 3 conv blocks, no BatchNorm | WeightedRandomSampler |
| `BatchNorm_Custom_CNN` | 3 conv blocks + BatchNorm | Class-weighted loss |
| `ResNet18_Transfer` | ResNet18 (ImageNet weights), dropout 0.3 + linear head | Class-weighted loss |

- **Image size:** 224 × 224
- **Normalisation:** ImageNet stats, `mean=[0.485, 0.456, 0.406]`, `std=[0.229, 0.224, 0.225]`
- **Train augmentation:** RandomResizedCrop(0.75–1.0), horizontal flip, ±10° rotation, colour jitter (brightness/contrast 0.2, saturation 0.1)
- **Eval transform:** resize + normalise only — augmentation is never applied at evaluation
- **Loss:** CrossEntropy with inverse-frequency class weights
- **Optimiser:** Adam, lr 3e-4 (ResNet) / 1e-3 (custom), weight decay 1e-4
- **Epochs:** up to 40, early stopping on **validation** macro F1, patience 12
- **Decision threshold:** grid-searched on **validation**, stored in the checkpoint

## 2b. CNN — cross-validated results (quote these)

5-fold stratified CV. Every image is scored exactly once by a model that never
trained on it, so the estimate rests on all **100 flooded positives** instead of
15. Threshold and early stopping are tuned on an inner validation slice carved
from each fold's own training data; the fold's test partition is never touched
until final scoring.

| Metric | Single split (n=75) | **5-fold CV (n=500)** | Fold std | **95% CI** |
| --- | ---: | ---: | ---: | :---: |
| Accuracy | 0.960 | **0.9580** | ±0.0319 | [0.9400, 0.9740] |
| Macro F1 | 0.939 | **0.9326** | ±0.0510 | [0.9029, 0.9583] |
| Flooded recall | 0.933 | **0.8600** | ±0.0962 | [0.7884, 0.9239] |
| Flooded precision | 1.000 | **0.9247** | ±0.0836 | [0.8700, 0.9717] |
| Flooded F1 | 0.903 | **0.8905** | ±0.0822 | — |
| Flooded ROC-AUC | 0.986 | 0.9792 | ±0.0212 | — |
| Flooded PR-AUC | 0.958 | 0.9509 | ±0.0433 | — |

**The single split was optimistic.** Its 0.933 flooded recall is *above* the
cross-validated 95% upper bound (0.924). Per-fold recall ranged 0.75 to 1.00.
The defensible claim is **0.86 flooded recall, ±0.10**.

This does not replace the held-out evaluation in `04_evaluation_engineer.py`:
that measures the exact deployed checkpoint, while CV measures the architecture
and training procedure — which is the thing a confidence interval can
legitimately be placed around.

```bash
python Stage02_DL/06_cross_validation.py --folds 5 --epochs 25
```

Output: `data/outputs/cnn_cross_validation.json`.

## 3. LSTM — water-level forecasting

### Data and split

`data/Engineered_History_Trend_Dataset.csv`, 8,760 hourly rows. Chronological
70/15/15, **no shuffling**. `StandardScaler` is fitted on the training slice
only. Validation and test windows begin at `split - LOOKBACK` so no sequence
straddles a boundary. Split boundaries are recorded in
`data/outputs/lstm_split_manifest.json`.

- **Lookback:** 72 hours
- **Features (4):** `water_level`, `rolling_mean_6h`, `rolling_std_6h`, `diff_t_1` — all strictly backward-looking, so there is no lookahead leakage
- **Architecture:** 2-layer LSTM, hidden size 64, dropout 0.2, linear head
- **Loss/optimiser:** MSE, Adam lr 1e-3, `ReduceLROnPlateau`
- **Early stopping:** on validation RMSE, patience 10 (triggered at epoch 70)

### One-step results

| Metric | Result |
| --- | ---: |
| MAE | 0.2284 m |
| RMSE | 0.7069 m |
| Test sequences | 1,314 |
| Average latency | ~0.17 ms/sample |

### Multi-step results — the horizon the API actually serves

The dashboard and `forecast_water_levels()` return a **6-step recursive**
forecast, where each prediction is fed back in as input. Only 1-step error used
to be measured. It is now evaluated at every served horizon:

| Horizon | MAE (m) | RMSE (m) | Samples |
| --- | ---: | ---: | ---: |
| +1 h | 0.1704 | 0.2956 | 250 |
| +3 h | 0.5090 | 1.2011 | 250 |
| **+6 h** | **0.7307** | **1.5980** | 250 |

**Error grows ~4.3× from step 1 to step 6.** Quoting the 1-step MAE as if it
described the 6-hour forecast overstates accuracy by a wide margin. The API
returns `expected_mae_at_horizon` so the caller sees the right figure.

### Out-of-distribution guard

Training distribution: **mean 3.167 m, std 1.613 m, range 2.307–18.278 m**.

Given inputs far outside that range the model extrapolates and returns
physically implausible output — fed a flat 10.0 m series (+4.2σ) it produced an
oscillating `8.50 / 9.28 / 6.63 / 8.45 / 6.04 / 7.27` instead of a flat ~10 m.
`forecast_water_levels()` now returns `in_distribution` plus a warning string
when any input exceeds ±4σ, and the dashboard renders that warning.

The dashboard's demo sequence was also replaced: it previously ran 8→15 m
(roughly +7.6σ), so the chart shown to a viewer was pure extrapolation. It now
uses a realistic in-range rising-river scenario (~2.9 → 5.4 m).

### Robustness

Gaussian perturbation (σ = 0.05 in scaled space) moves MAE from 0.22843 to
0.22842 and RMSE from 0.7069 to 0.7084 — the model is stable to small input
noise. This is a sensitivity check, not a substitute for the test metrics.

## 4. Interpretability

`02_eda_engineer.py` produces saliency-style overlays under
`data/outputs/saliency_maps/` and `gradcam_visualizations/`.

**Limitation, unchanged:** these are dark-pixel-overlap screens, not true
Grad-CAM. They cannot establish that the network attends to water rather than
shadow. A genuine Grad-CAM implementation remains outstanding, and the
wet-asphalt false-positive mode cannot be isolated numerically without localised
annotations.

## 5. Model save / load

| Artifact | Contents |
| --- | --- |
| `data/models/disaster_cnn.pt` | state dict, class names, image size, validation-tuned threshold, architecture flags, class weights |
| `data/models/water_level_lstm.pt` | state dict, lookback, input size |
| `data/models/water_level_scaler.joblib` | fitted `StandardScaler` (also the source of the training distribution used for the OOD check) |

Checkpoints load with `weights_only=True`. `torch.load` otherwise unpickles
arbitrary objects, which makes loading a checkpoint equivalent to executing it.

Both models are **cached at module level** and loaded once. `predict_image()`
previously re-read the 44 MB checkpoint and rebuilt ResNet18 on every request
(~230–450 ms per call).

> A third model (`severity_model.joblib`, a logistic-regression zone-risk
> classifier) has been **removed**. It duplicated Stage 01's task on the same
> labels and was never called by the dashboard or any other stage.

## 6. Inference API

```python
engine = DLIntegrationEngine()

engine.predict_image("Stage02_DL/data/raw/scene.jpg")
# {"label": "flooded", "confidence": 0.94, "flooded_probability": 0.94, "image": "data/raw/scene.jpg"}

engine.forecast_water_levels([3.1] * 72, horizon=6)
```

```json
{
  "forecast_water_level": 3.05,
  "forecast_water_levels": [3.05, 3.01, 2.97, 2.94, 2.91, 2.89],
  "horizon": 6,
  "lookback": 72,
  "in_distribution": true,
  "distribution_check": {
    "in_distribution": true,
    "max_sigma_from_training_mean": 0.04,
    "training_mean_m": 3.167,
    "training_std_m": 1.613,
    "sigma_threshold": 4.0
  },
  "expected_mae_at_horizon": 0.7307

```

`predict_image()` confines paths to `Stage02_DL/data/raw/` (path-traversal
guard). `health_check()` runs a real forecast rather than only checking that
model files exist.

## 9. Known limitations

1. **500 images total.** Cross-validation and bootstrap CIs now quantify the
   uncertainty honestly, but ±0.10 fold-to-fold variation on flooded recall is a
   data-volume limit that no amount of methodology can remove.
2. **No true Grad-CAM**; wet-asphalt false positives cannot be isolated.
3. **Recursive forecast degrades sharply** with horizon (measured above).
4. **No exogenous variables** in the forecaster — rainfall is not an input, which
   is the most likely reason absolute-scale errors persist.
5. **CNN training is CPU-slow** (~80 minutes for the three-experiment benchmark).
6. **Stage 02 does not exchange data with Stage 01 or Stage 03.**
